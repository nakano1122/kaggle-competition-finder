# ドメイン駆動設計

最初に `README.md`、`docs/specification.md`、既存の `domain/` と永続化スキーマを読む。利用者の言葉を起点にし、テーブル名や外部 API のレスポンスをそのままドメインの中心にしない。

- このアプリでは「研究・開発実績」「保存済み検索クエリ」「コンペ候補」「お気に入りコンペ」を基本語彙として扱う。Kaggle API のデータは境界で `コンペ候補` に変換し、UI や D1 に外部 API 固有の形を漏らさない。
- `domain/` には、意味のある不変条件・振る舞い・変換規則を置く。例として、空白だけの実績を登録しない、英語検索キーワードを最大 3 件にする、コンペ ID を基準に候補を重複排除する、といった規則を一箇所に保つ。
- 値オブジェクト、entity、domain service は規則や識別性を表す場合だけ作る。単なるデータ転送や列の写し替えのために class や型の層を増やさない。
- D1 のレコード変換、Kaggle 通信、Hono のリクエスト検証、React の表示状態は domain の外側に置く。domain は Cloudflare、React、Drizzle に依存させない。
- 型の安全性で表現できる規則は型を使い、実行時に必要な規則は明示的な関数で検証する。`as` による型の押し通しを避け、失敗を呼び出し元が扱える形にする。

業務規則を変更したら、正常系と境界値を単体テストで確認する。新しい語彙や規則が仕様にない場合は、実装前にユーザーへ確認する。
